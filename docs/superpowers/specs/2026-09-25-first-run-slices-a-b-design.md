# Krellbot first-run, slices A and B — design

## Purpose and boundary

A new user should install a local, open-source engine without obtaining Python or reading developer setup instructions, land in its gated browser UI, and immediately understand where keys and data live. The free engine and CLI remain first-class. This release does **not** claim a connected exchange, unlocked pack, armed strategy, or verified live trade: key entry, redemption, paper arming, and live-path validation belong to slices C, D, and G. A/B must expose a real dashboard and honest next steps rather than a decorative or false-success wizard.

The source of truth is `d4rk-pri0r/krellbot` at the inspected 0.9.1 line. The separate `krellbot-cloud` repository owns the public site and installer endpoint. The engine repository was clean at survey; the site repository was ahead of origin and had untracked `brand/` work. Implementation must isolate site edits from that work and never overwrite it. The primary domain returned 403 from this environment, while the alternate Pages endpoint served the site but returned 503 for installer scripts; a deployed installer is not established by this design.

## Existing seams and non-negotiables

`src/krellbot/ui/server.py` already supplies a stdlib `ThreadingHTTPServer` fixed to `127.0.0.1`, a 32-byte token in the URL, session/CSRF cookies, Host and Origin checks, no-store responses, disk views, and paper-only POSTs. Preserve this server and the seven existing contract tests. `cmd_ui` prints a token URL but does not open a browser. `src/krellbot/ui/static/` is small local HTML/CSS/JS. `functions/api/install.js` currently verifies a wheel SHA-256 but requires Python 3.10 on all platforms, optionally skips signature verification, installs network-resolved dependencies, and does not launch the UI. `scripts/release.py` emits wheel checksums and optionally signs them; no frozen artifact pipeline is established.

Never add network fetches to server rendering. User-initiated docs/source exits are fixed allowlisted routes; no arbitrary redirect or outbound static-asset URL. Never expose exchange secrets, license keys, journal details, or balances in the install/first-run flow. Live arm stays forbidden from the UI. Telemetry stays opt-in. `KRELLBOT_HOME` and all existing CLI commands remain compatible.

## Slice A — release, installer, and opening the local UI

### Artifact and trust model

Build per-user, one-directory frozen distributions around the existing Python package, with bundled static assets and OS-keyring backends. The OS/architecture release matrix covers Windows, macOS, and Linux variants actually offered on the site; an unsupported architecture receives an explicit error instead of another artifact. Pin Python/package inputs via the project lockfile and record the build source revision and version. Do not ship a wheel-only Windows path that depends on preinstalled Python, copy a virtualenv entry-point executable away from its interpreter, or claim that a digest alone is an independent publisher signature.

A release job emits an immutable, versioned manifest with artifact URL, filename, size, OS, architecture, version, and SHA-256. The public `/api/install?os=...` response embeds literal release-pinned coordinates and digest; it must return 503 rather than emit a partial installer when that metadata is absent or malformed. A short readable shell/PowerShell installer downloads into a per-user staging directory, checks the expected digest *before* extraction or replacement, validates archive layout against traversal, stages side-by-side, and atomically selects the new version only after smoke checks. It leaves the prior version intact on failure. No administrator or root privileges by default. A stable per-user launcher lands on `~/.local/bin` for POSIX or `%LOCALAPPDATA%\Krellbot\bin` for Windows, with PATH setup explained and checked. The data home remains independent of installed binaries. The initial installer runs the local command that opens the browser; subsequent `krellbot ui` remains the existing CLI and `krellbot ui --open` is an opt-in convenience. Duplicate launch behavior must be deterministic and must never print/reuse a stale gate token.

The minimum viable first-run is a verified local artifact plus a newly started loopback server and browser URL bearing *that process's* token. OS scheduler installation belongs to the later arm step, not to the installer. Uninstall removes only managed binaries/launcher; retaining the data home is the default. Document optional scheduler removal and explicit data deletion separately. macOS notarization/code-signing and Windows Authenticode are release hooks, not claimed until valid credentials and verification are exercised. Unsigned artifacts are labeled unsigned in install docs and output. A checksum fetched over the same HTTPS origin as a mutable artifact offers transport/integrity assurance, not independent authenticity; version-pinned release coordinates and signed publisher releases are the eventual higher bar. Do not publish copy-paste one-liners for a platform without a built and verified artifact.

### Engine launcher and health

Keep `DashboardServer`'s bind and security checks. Extract an injectable `ui --open` launcher: start on port 0, read the bound port and current token, open precisely `http://127.0.0.1:<port>/<token>/` with the default browser, keep serving until shutdown, and display a usable URL if browser opening fails. No extra unauthenticated discovery endpoint or broad bind. The CLI's existing `ui --port` behavior remains. `doctor` distinguishes installation readiness (runtime, home permissions, keyring backend availability, scheduler *availability*, UI bind) from trading readiness (keys, recent tick, armed packs). A fresh install can be installation-ready without keys or a tick; do not silently suppress operational warnings. On Linux, absent Secret Service must be shown accurately; never silently downgrade to a plaintext durable credential store.

### Release verification

Automated tests exercise manifest validation, digest mismatch, archive traversal, staging rollback, idempotent install/uninstall, launcher URL/browser injection, loopback binding, frozen asset loading, and the site's rendered script for each OS. CI builds and smokes the artifact on the matching OS in a clean user profile. Manual clean-machine checks verify PATH, fresh `doctor` readiness, browser opening, home permissions, and uninstall on each platform. A local Mac test alone is not cross-platform acceptance.

## Slice B — wizard shell, trust screen, and visual system

The local UI loads under the existing gate URL. Routes are scoped below the token, e.g. welcome, security, next steps, dashboard, with deep-link navigation inside the token prefix and no secret stored in browser persistence. First launch defaults to Welcome. A small atomic 0600 local preference may record that the user chose to enter the dashboard; it denotes *visited*, not *onboarding complete*. A later launch can default to the dashboard with a clear resume-setup affordance. Browser back/forward and wizard Back do not mutate trading state.

- **Welcome:** three short statements: free open-source local engine, keys stay on this machine, official packs are optional and recommended. Continue, plus user-initiated source/docs links.
- **Security posture:** show the detected backend name (macOS Keychain, Windows Credential Manager, Linux Secret Service, or an unavailable/failing state), resolved data home and POSIX permissions, trade-only/withdraw-off policy, `127.0.0.1` bind, and the fact that UI live arm is refused. Unknown permissions must not become a green check. A backend failure gives a specific diagnostic and CLI/doctor next action, not a fake connected state.
- **Next steps:** exchange connection and official/custom strategy steps are clearly labeled as subsequent slices. Offer the real existing dashboard now and concise CLI paths without implying those incomplete UI operations have happened. No disabled CTA masquerades as success; the free path stays visible.
- **Dashboard:** retain functioning paper arm, disarm, stop-all, pending-version adoption and the existing disk views. Re-skin without changing action semantics. No ROI or performance figure without a window, fees/slippage basis, venue, and past-performance caveat.

Use the site's near-black canvas and precise cyan as the app's one primary interactive accent; lime, if retained, is a restrained status token rather than a second CTA palette. Tight hierarchy, tabular figures, monospaced IDs, responsive density, no looping effects, no CDN or third-party fonts/scripts, and reduced-motion support. Define empty, loading, error, offline, paper, and live-armed read-only states, but do not add live-arm controls. Keyboard focus and contrast are release checks. CSP and `Referrer-Policy: no-referrer` prevent gate-token leakage on fixed external exits; target pages never receive the token URL. Only allowlisted, user-initiated docs/source navigation is external. Static assets remain entirely local.

The server computes a presentation-only trust snapshot from local `paths`, `doctor`, and keyring-backend checks; it does not read raw secret values to render the trust screen. The view model keeps raw license tokens and credentials out of HTML/JS. All POSTs retain session cookie, token, CSRF form value and Origin requirements. Any new read route still requires the token and Host allowlist. The existing stop-all and adopt-while-long tests must continue passing.

## Failure states, testing, and documentation

A blocked site, missing release metadata, bad digest, unsupported architecture, absent keyring backend, unavailable browser, or failed frozen build ends with a specific non-success message and no partially selected installation or green trust indicator. Existing installations and `$KRELLBOT_HOME` survive installer failure. The site may link to a manual verified download when a one-liner cannot run, but must not advertise that path as completed installation.

Engine tests: existing 300-test baseline, UI contract tests, wizard route/navigation/state tests, trust backend/permission fakes, browser-launch injection, static-resource URL allowlist, no-secret-in-view tests, and release helper unit tests. Site tests: installer script rendering and fail-closed metadata cases, version/OS/architecture matrix, digest/traversal/rollback behavior. Run `uv run pytest -q` and the site repository's Node test suite; run frozen smoke tests on each OS before claiming installer parity. Update README, SECURITY.md, engine docs (`getting-started`, `dashboard`, `security`, `service`) and the published site's corresponding pages and installation copy in the same release train. Keep the docs' live and Coinbase statements synchronized with actual tested behavior rather than copying contradictory older text.

## Explicit exclusions and release gate

No exchange-key web form, activation redemption, checkout integration, pack picker, scheduler installation, advanced studio, remote dashboard, telemetry change, or easier live gate in A/B. C/D/E/F/G remain later vertical slices. A/B implementation can be reviewed incrementally, but its completion claim requires usable verified artifacts and a deployed site endpoint for each advertised OS; otherwise report the platform-specific gap, not a completed mission.
